# 第32课：GDD结构详解

## Learning Objectives

- 掌握从概念文档到GDD的完整文档演化流程
- 理解高层次文档、中层/低层文档的核心区别和编写要点
- 学会使用模块化方法构建**Game Design Manual（游戏设计手册）**
- 掌握文档中必备信息和可选信息的组织结构

## Core Idea

游戏文档设计过程遵循一个自然的演化流程：**想法 -> 概念文档 -> 高层次文档 -> 中层/低层文档 -> GDD -> 支持文档**。每一步都在前一阶段的基础上增加细节和深度。

> [!TIP] Key Insight
> 在技术写作中有一个重要法则——**每一页都应该是第一页**。这并不意味着每份文件都要解释所有内容，而是不要将读者的知识视为理所当然。始终添加必要的链接和参考文献，让读者能够了解他们需要知道的信息。

**必备信息清单：**
- 游戏名称（标注是否为工作标题）
- 平台和预计发布日期
- 游戏介绍（1-2段，包括总体想法、主要机制和目标）
- 玩家目标与胜负条件（最好放在第一页）
- 系统、机制与部件（最长的关键部分）
- 控制方案（多平台游戏需提前规划控制器布局）
- UI说明（尤其是手机游戏）
- 屏幕流（Screen Flow）
- 艺术与音乐参考

## Worked Example

文档演化流程详解：

1. **Concept Document（概念文档）**：读者浏览不应超过2分钟。使用短句子、电报式语言，只传达必要信息。应包含游戏名称、口号、概述（类型、目标受众、平台等）、5个以内的关键词列表、主题描述和参考图片

2. **High-Level Document（高层次文档）**：约10-15页，创意成形的时刻。包含引言（100-150字描述游戏）、概述（从概念文档提取）、主题（背景故事和艺术风格）、**3C规则（Camera, Character, Controller）**——即玩家如何看、如何互动、如何玩

3. **Mid/Low-Level Document（中层/低层文档）**：开始扩展机制细节。聚焦于主要机制和游戏核心方面，不需要对列出所有内容都过于细致化。例如，天赋系统在高层次文档中仅是声明，而在低层次文档中则需要讨论天赋如何影响系统、科技树如何运作

4. **GDD（游戏设计文档）**：有两种创建方式
   - **单文件方法**：不推荐。复制低层文档并持续迭代扩展
   - **模块化方法（推荐）**：创建GDD手册，使用多个小文档分别处理游戏的某个特性或方面

> [!IMPORTANT]
> 模块化方法虽然需要更多时间来制作和组织，但从长远来看更具优势：让你更清楚自己的工作进展、可以处理更小的文档从而专注于具体事务、系统可扩展性更强、更新和维护更加简单。

## Practice

> [!QUESTION] Self-check
> 假设你正在为一个包含"战斗系统、经济系统、角色成长系统"三个核心系统的游戏编写GDD。请说明你会采用哪种GDD组织方式，并解释各个系统应该分别在文档演化的哪个阶段开始详细记录。

<details>
<summary>Reveal answer</summary>

**推荐采用模块化方法（Game Design Manual）进行组织。**

组织方式：
- 创建一个主索引文档（GDD手册），包含项目概述、全局信息和三个系统的链接
- 为每个系统创建独立的文档：`战斗系统.md`、`经济系统.md`、`角色成长系统.md`
- 如果某个系统特别复杂（如角色成长系统包含技能树、属性成长、装备等多个子系统），可进一步拆分为子文档

各系统的文档演化阶段：

1. **概念文档阶段**：用1-2句话概括每个系统的核心玩法和定位。例如"经济系统驱动玩家之间的资源交易和流通"

2. **高层次文档阶段**：每个系统分配1-2页，描述其目标和大致运作方式，不涉及具体数值。例如战斗系统描述"实时动作战斗，包含近战和远程两种模式"

3. **低层文档阶段**：从最重要的系统开始深入。如果战斗系统是核心体验，优先为其编写详细的低层文档——包含武器参数、伤害计算公式、战斗状态机等

4. **GDD模块化阶段**：每个系统成为独立的文档，包含完整的系统描述、机制详解、UI示意、屏幕流和相关资产引用。不同系统的文档之间通过同步块或链接保持引用关系
</details>
